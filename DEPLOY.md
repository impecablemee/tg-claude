# Разворачивание на своём сервере

По порядку. Порядок не менять: каждый шаг ломается заметно только если
предыдущий уже работает.

Подробный вариант этого же на английском, с обоснованием каждого решения, —
[SETUP.md](SETUP.md). Здесь — короткий рабочий путь.

---

## 0. Что нужно иметь заранее

- Linux-сервер, который вы контролируете. 2 vCPU / 4 ГБ хватает с запасом.
  На нём живёт всё: база, сессии, репозиторий. Наружу не уходит ничего.
- Telegram на телефоне у каждого, кто подключается, и его внимание на время подключения.

## 1. Код на сервер

```bash
sudo apt update && sudo apt install -y python3-venv git sqlite3

git clone <адрес-этого-репозитория> ~/tg-claude && cd ~/tg-claude
python3 -m venv connector/.venv
connector/.venv/bin/pip install -r connector/requirements.txt

connector/.venv/bin/python connector/guard_readonly.py     # должно напечатать OK
```

Последняя строка — смысл всего шага: **на своей машине, до подключения хоть
одного аккаунта**, вы получаете доказательство, что этот код не умеет отправлять.
Не обещание, а прогон.

## 2. База

```bash
mkdir -p connector/data
connector/.venv/bin/python -c "import sqlite3; sqlite3.connect('connector/data/tg.db').executescript(open('connector/schema.sql').read())"
```

Схему разворачиваем питоном, а не утилитой `sqlite3`: питон уже стоит (venv из
предыдущего шага), а `sqlite3` в минимальной установке Ubuntu отсутствует —
`command not found` на этом шаге ловится на живом сервере. В `apt install` выше
она добавлена ради примеров с запросами ниже.

Схема — единственное место, где описано, что хранится. Читается за пять минут,
и это стоит сделать до подключения людей: там же написано, чего мы НЕ храним.

## 3. Первый человек

Полностью и с формулировками для разговора — [AUTH.md](AUTH.md). Коротко:

```bash
connector/.venv/bin/python connector/tg_login.py --slug anna --folder Work
connector/.venv/bin/python connector/tg_sync.py  --slug anna --limit 50
```

## 4. Живая доставка

Telegram сам присылает новые сообщения в открытое соединение — опрашивать ничего
не надо, задержка секунды. Один сервис на аккаунт:

```bash
sudo cp connector/tg-live.service /etc/systemd/system/tg-live@.service
sudo nano /etc/systemd/system/tg-live@.service     # проверить User= и пути
sudo systemctl daemon-reload
sudo systemctl enable --now tg-live@anna
journalctl -u tg-live@anna -f
```

**Крон с `tg_sync.py` при этом не нужен и не должен стоять.** Ключ авторизации
Telegram — ресурс единственного держателя: два процесса на одном ключе видятся
как вход с двух адресов, и ключ ОТЗЫВАЕТСЯ — человеку придётся сканировать QR
заново. Живой процесс делает все работы сам: слушает события, раз в
`--scope-seconds` (по умолчанию 60) перечитывает состав папки и раз в
`--reconcile` минут (по умолчанию 15) прогоняет обычную сверку тем же
соединением — она ловит удаления и всё, что могло пройти мимо в минуту разрыва
связи.

Таймера два, потому что это разные по цене работы. Состав папки — один запрос,
поэтому раз в минуту: чат, вынесенный из папки, перестаёт читаться сразу, а не
через четверть часа. Сверка обходит КАЖДЫЙ чат, и в минутном режиме упёрлась бы
в `FLOOD_WAIT`.

Если обновления сломаются, живой режим деградирует до свежести этой сверки, а не
до тишины. Отличить одно от другого можно по времени последнего события:

```sql
sqlite3 connector/data/tg.db \
  "SELECT slug, last_sync_at FROM accounts;"
```

Разовый синк остаётся под рукой для первого наполнения и разбора:

```bash
connector/.venv/bin/python connector/tg_sync.py --slug anna --limit 200
```

Выполнять его, пока работает `tg-live@anna`, нельзя — он и не выполнится:
блокировка аккаунта занята, и скрипт скажет об этом прямо.

Чем закончились сверки:

```sql
sqlite3 connector/data/tg.db \
  "SELECT account_slug, status, chats_seen, messages_new, error FROM sync_runs ORDER BY started_at DESC LIMIT 10;"
```

`ok` — прошло · `flood_wait` — попросили подождать, не поломка · `failed` — смотреть `error`.

## Ежедневная эксплуатация

[ops/DAILY.md](ops/DAILY.md) — что смотреть каждый день и как понять, что данные
свежие. Ключевой инструмент — `tg_coverage`: он отвечает не «сколько сообщений»,
а «по каким чатам мы вообще смотрели и когда». Разница между «нет сообщений» и
«ни разу не синхронизировали» — та, из-за которой принимают неверные решения.

## Резервная копия

Копировать нужно два места, и относиться к ним по-разному:

| Что | Зачем | Секретность |
|---|---|---|
| `connector/data/tg.db` | вся прочитанная переписка | как к переписке |
| `connector/sessions/` | ключи аккаунтов | **как к паролям** |

`sessions/` в git не попадает (`.gitignore`) и в общие хранилища класть нельзя.
Потеря `sessions/` не страшна: люди пересканируют QR. Утечка `sessions/` — это
утечка их аккаунтов целиком.

## Обновление

```bash
cd ~/tg-claude && git pull
connector/.venv/bin/pip install -r connector/requirements.txt
connector/.venv/bin/python connector/guard_readonly.py     # снова OK
```

Страж после каждого обновления — не ритуал: он единственный, кто заметит, что в
код завезли пишущий вызов.
