# Claude на своём ноутбуке, данные на сервере

Схема, в которой **Claude Code не запускается на сервере вообще**. Сервер делает
одну работу — забирает новые сообщения в базу. Claude живёт у вас на компьютере,
под вашим личным доступом, и читает эту базу через SSH.

Это то, что нужно, если вы хотите: положить что-то в чат, а потом спросить у
своей локальной сессии Claude «разбери последнее сообщение вот в этом чате».

```
   ВАШ НОУТБУК                          ВАШ СЕРВЕР
   ───────────                          ──────────
   Claude Code            ── ssh ──▶    mcp_server.py  ──▶  tg.db
   (ваш доступ)                         (только чтение)      ▲
                                                             │
                                        tg_live.py, сервис ──┘
                                        (открытое соединение,
                                         сессии людей)
```

## Чем это лучше, чем Claude на сервере

| | Claude на сервере | **Claude на ноутбуке** |
|---|---|---|
| Чей доступ к Claude | общий на сервере, надо решать чей | **личный, у каждого свой** |
| Кто платит | одна учётка за всех | каждый за себя |
| Кто видит переписку | процесс на сервере | ваш ноутбук, ваша сессия |
| Ставить Claude на сервер | обязательно | **не нужно вовсе** |
| Работает офлайн | — | нет, нужен ssh до сервера |

Побочно решается неприятный вопрос «чья подписка крутится на сервере»: никакой.
У каждого своя, локально.

## Что ставится на сервер (один раз)

Всё из [DEPLOY.md](DEPLOY.md): Claude Code на сервер не ставится вовсе.
То есть: код, venv, база, сессии людей ([AUTH.md](AUTH.md)) и живой сервис
`tg-live@` — он держит соединение с Telegram и он же раз в пятнадцать минут
прогоняет сверку. **Крона с `tg_sync.py` рядом с ним быть не должно**: два
процесса на одном ключе Telegram — отзыв ключа, а не удвоение скорости.

Проверить, что серверная часть жива:

```bash
ssh ops@server 'systemctl is-active tg-live@anna; \
  sqlite3 ~/tg-claude/connector/data/tg.db "SELECT slug, last_sync_at FROM accounts;"'
```

`last_sync_at` двигается на каждом принятом событии и на каждой сверке. Значит,
даже на молчащем аккаунте он обязан обновляться минимум раз в пятнадцать минут:
не двигается дольше — слушатель мёртв, и это видно без догадок.

Запускать `tg_sync.py` руками при поднятом сервисе не нужно и не выйдет — он
откажется («another sync holds …»), потому что аккаунт занят живым процессом.

## Что ставится на ноутбук

Только Claude Code и доступ по ssh к серверу по ключу (без пароля — иначе Claude
будет висеть на запросе пароля):

```bash
ssh-copy-id ops@server
ssh ops@server 'echo ok'        # должно ответить ok без единого вопроса
```

Дальше — папка, из которой вы будете запускать Claude, и в ней один файл:

```bash
mkdir -p ~/tg-claude-local && cd ~/tg-claude-local
```

`~/tg-claude-local/.mcp.json`:

```json
{
  "mcpServers": {
    "telegram": {
      "command": "ssh",
      "args": [
        "ops@server",
        "cd ~/tg-claude && TG_DB=connector/data/tg.db connector/.venv/bin/python connector/mcp_server.py"
      ]
    }
  }
}
```

Это весь клиент. MCP общается по stdin/stdout, а `ssh host 'команда'` ровно такую
пару труб и даёт — поэтому промежуточного сервиса, порта и токена здесь нет.

Проверка:

```bash
cd ~/tg-claude-local && claude
```

и спросить `какие telegram-аккаунты подключены` — ответ придёт с сервера.

## Полный проход на живом примере

Как это выглядит целиком, с реальными именами. Папка в Telegram называется `Work`,
в ней лежат рабочие чаты, среди них `клиент: acme`.

**Один раз, на сервере** — подключить аккаунт и назвать папку:

```bash
ssh ops@server
cd ~/tg-claude
connector/.venv/bin/python connector/tg_login.py --slug anna --folder Work
connector/.venv/bin/python connector/tg_sync.py  --slug anna --limit 200
```

**Дальше — только у себя на ноутбуке.** Кинули что-то в `клиент: acme` с телефона,
открыли терминал:

```bash
cd ~/tg-claude-local && claude
```

```
обнови и разбери последнее сообщение в чате «клиент: acme»
```

Claude возьмёт `tg_history` по этому чату; если живого сервиса нет — сначала
`tg_refresh`, чтобы забрать только что отправленное. Сервер при этом Claude не
запускает — он вообще про него не знает.

**Имя чата можно писать как удобно.** Точное название выигрывает у подстроки:
`клиент: acme` находит именно его, даже когда рядом лежит `клиент: acme (архив)`.
Регистр и кириллица не важны — `КЛИЕНТ: ACME` и `Иванова` находятся так же.
А вот просто `клиент`, когда таких чатов три, вернёт список кандидатов: назвать
чат точнее должен человек, а не система угадать за него.

## Ваш рабочий сценарий: положил в чат → сразу спросил

Если на сервере поднят живой сервис ([DEPLOY.md](DEPLOY.md), шаг 4), сообщение
попадает в базу за секунды — спрашивать можно сразу, ничего обновлять не надо.

Инструмент **`tg_refresh`** нужен в двух случаях: живого сервиса нет и синк
ходит по расписанию, либо вы хотите убедиться, что видите самое последнее.

Спрашивайте так:

```
обнови и разбери последнее сообщение в чате «c:easy»
```

Claude вызовет `tg_refresh`, затем `tg_history`. Если хотите быть уверены —
скажите прямо: `сначала tg_refresh, потом последние 5 сообщений из «c:easy»`.

### Вложения

«Покажи, что там в PDF» работает и при поднятом живом сервисе, хотя ключ Telegram
занят им постоянно: заявка кладётся в базу, качает держатель ключа, файл доходит
за секунды. Ответ `queued: true` означает «спросите ещё раз через мгновение», а
не «не вышло».

`tg_refresh` возвращает, что именно изменилось: `new_messages: 0` означает
«синк сходил и нового нет» — это ответ, а не сбой. Если по аккаунту в этот момент
уже идёт плановый синк, вернётся `already_running: true`: сообщения приедут,
просто не этим вызовом.

**Не просите обновлять перед каждым вопросом.** Синк ходит в Telegram, а Telegram
считает частоту: дёргать его на каждую реплику — способ поймать `FLOOD_WAIT` на
ровном месте. Обновление нужно, когда спрашиваете про только что случившееся.

## Папка — по-прежнему граница

Читается только то, что человек положил в свою папку Telegram ([AUTH.md](AUTH.md)).
Локальный Claude ничего в этом не меняет: он видит ровно ту же базу, что и любой
другой читатель, и ровно те же чаты.

## Несколько человек

У каждого свой `~/tg-claude-local/.mcp.json` и свой ssh-ключ на сервер. База одна,
и это осознанно: вопрос «что мы обещали клиенту» должен иметь один ответ, а не
пять личных.

Если нужно, чтобы человек видел только свои чаты — заводите ему отдельного
пользователя на сервере с отдельной базой. Разграничение внутри одной базы
инструментами MCP не делается: `tg_history` не спрашивает, кто её позвал.

## Если что-то не работает

| Симптом | Причина |
|---|---|
| Claude не видит инструменты `tg_*` | запущен не из папки с `.mcp.json` |
| `ssh` спрашивает пароль | нет ключа; MCP-клиент не умеет его ввести и просто зависнет |
| «no chat matching …» | чат не в папке, или синк по этому аккаунту ни разу не проходил — спросите `tg_coverage` |
| Ответ по вчерашним данным | не поднят живой сервис и не позвали `tg_refresh` |
| Голосовое без текста | расшифровка ещё не прошла либо недоступна на этом аккаунте — `tg_accounts` покажет, что именно; «нет текста» ≠ «ничего не сказали» |
| «queued: true» на вложении | ключ Telegram у живого сервиса, он и качает — спросите вложение ещё раз через несколько секунд |
| «ambiguous» на понятном названии | два чата подходят под этот кусок названия; назовите точно или добавьте `account=` |
| `command not found: connector/.venv/bin/python` | в `.mcp.json` путь до venv на сервере другой |
